# 多 agent 并行处理与审阅工作法（MirrorpondHUD）

- 日期：2026-11-14
- 状态：已按 builder check 修订，待批准
- 适用：本仓库内由「Lead + 若干工作 agent」并行完成审阅、实现/重构、修 bug、文档调研四类工作
- 样板作业：审阅当前未提交改动 + 全仓库红线抽检（本文件 §6），**只读**

---

## 1. 为什么需要它

单 agent 做完整仓库的工作有两个天花板：上下文装不下整个 `src/`，且作者自查存在盲区。多开 agent 不是答案本身——没有收口的多 agent 只会把"漏查"换成"冲突、重复、误报、验证互相踩"。

本仓库的具体形状决定了收口点：

- 代码量约 5.5 万行手写 C#、153 个文件，单 agent 一次审不完；
- 真正共享、且一改就影响全局的东西很少：`Directory.Build.props` 的 `<Version>`、`docs/version-history2.md`、Contracts 的序列化 DTO、`bin/obj`；
- 验证链是**单实例串行**的（`--selftest` / `--screenshot` 撞互斥体，build 共享 `bin/obj`），并行 agent 各自跑验证必然互相踩；
- 已有 `docs/review/review-2.44.2.md` 这样 1,300 行、P0–P3 四级、带编号与附录的评审成例，格式与口径有先例可循。

## 2. 目标、非目标与反目标

**目标**

1. 让 N 个工作 agent 并行推进互不阻塞，且 Lead 始终是唯一收口人；
2. 让审阅产出可定级、可复核、可追踪（每条 finding 有证据、有编号）；
3. 让验证门禁在并行下仍然可信——不出现"两个 agent 各自绿灯、合起来是红的"；
4. 同一套方法覆盖四类工作，不因工作类型换一套流程。

**非目标**

- 不追求全自动无人值守；Lead 的裁决与汇总不可省；
- 不引入 CI、analyzers、第三方 NuGet（§1 项目约束）；
- 不替代 `docs/superpowers/plans/` 里的实施计划流程；本方法管"怎么并行干"，plan 管"干什么"。

**反目标**（即使技术上跑通也算失败）

- 并行作业产出一堆无法复现的"疑似问题"，把定级成本推给 Lead；
- 为并行而拆任务，导致一次提交里混进多个主题（违反 §9 提交纪律）；
- 验证门禁被跳过或被伪造绿灯；
- 报告宣称的覆盖范围超过实际做过的范围。

## 4. 备选方案与取舍

**A. 维度切片 + 非作者交叉复核**（选定）
按 AGENTS 红线把审阅维度分成 3 组，每 agent 认领一组，同时下发「必查文件清单」保证覆盖；P0/P1 必须由第二个 agent 独立复核后定级。
- 换取：维度与红线一一对应，三人对"什么算问题"天然一致；只读无写冲突；交叉复核直接压误报。
- 代价：同一文件被多人读；跨维度问题（如空 catch 同时掩盖了文档承诺）要靠 Lead 合并补。

**B. 目录/程序集切片**
每 agent 认领一组 `src/` 子树，红线清单人手一份，Lead 横向审计。
- 换取：覆盖确定、零重叠。
- 代价：三人对红线尺度把握必须完全一致，否则定级打架；切缝（Contracts 引用关系、插件与宿主边界）最易漏。

**C. 两阶段热点深挖**
第一轮快速扫全仓产热点，Lead 收敛 Top N 后第二轮深挖。
- 换取：预算花在真问题上。
- 代价：两轮延迟；本仓库已有大量历史 review 可当先验，冷启动收益低。

选 A，吸收 B 的「必查清单」思路：**维度负责查得深，清单负责查得全**。C 保留为以后全仓大规模审计时升级为 workflow 脚本扇出的路径。

## 5. 方法本体

### 5.1 三个收口

任何并行作业都必须同时满足这三道收口，缺一道就不许开工。

1. **写域收口**：每个任务卡声明写域（文件或目录前缀）。写域重叠 → 串行或拆任务。公共文件（`Directory.Build.props`、`version-history2.md`、`AGENTS.md`、`.editorconfig`、`global.json`、`.gitignore`、`tools/*`）只归 Lead。
2. **审阅收口**：作者 ≠ 审阅者。实现类任务完成后由非作者 reviewer 看 diff；审阅类任务由第二个 reviewer 复核 P0/P1。
3. **验证收口**：build / TestRunner / `--selftest --isolated` / 截图 / `dotnet format --verify-no-changes` / 空 catch 棘轮由 Lead 或指定 Verifier **串行**执行，一次一个，粘贴真实输出进报告。禁止并行跑、禁止"我本地跑过了"。

### 5.2 角色

| 角色 | 人数 | 权限 | 职责 |
| --- | --- | --- | --- |
| Lead | 1 | 唯一写公共文件、唯一提交、唯一裁决 | 拆任务卡、分派、裁决争议、去重定级、汇总产出、跑最终门禁 |
| Worker | N（本次 3） | 只写自己任务的写域 | 执行任务、产出结构化结果、自证证据 |
| Reviewer | 由 Worker 交叉担任 | 只读 | 复核他人 P0/P1、审阅他人 diff |
| Verifier | 可由 Lead 兼 | 跑命令 | 串行执行验证链、贴原始输出 |

Worker 是 Lead spawn 的独立 durable teammate（Agent Teams），并行执行、文件系统共享；Lead 不把工作交给"子 subagent 再分发"，因为被委派的 subagent 不能再 spawn。

### 5.3 任务卡契约

每张卡必须含：`ID`、目标（一句话可验收）、输入（文件/文档/清单）、**写域**、验收命令（可为空，只读任务写"只读"）、依赖卡、产出路径、时间盒。

验收命令为空且写域非空 → 直接退回。`--selftest` 类命令在卡片上标注"串行门禁，由 Verifier 执行"。

**结果信封**：Worker 回传的每条 finding 必须是同一形状，缺字段即退回：

```
{ id: "W2-01", level: "P0|P1|P2|P3", file: "相对路径", line: 行号或"文件级",
  触发条件: "...", 后果: "...", 证据: "引用代码/命令输出", 建议: "最小修法或处置" }
```

只读取证类任务另附「覆盖说明」（读过哪些文件、跑过哪些命令）与「待复核」项；实现类任务另附「改动文件清单 + 已跑命令 + 退出码」。

### 5.4 并行分派规则

- 写域按**程序集边界**切最稳：`src/Contracts/**`、`src/UiKit/**`、`src/Plugins/<Name>/**`、其余 `src/**` 各自独立。
- 一张卡跨多个程序集 → 拆卡或标为"Lead 独占"。
- 写代码的任务每张卡一个 `git worktree` 分支（`using-git-worktrees` 技能），避免 `bin/obj` 与单实例互斥体冲突；只读任务不需要 worktree。
- **同时写卡在途上限 3 张（含 Lead 的公共文件写卡）**，即最多 2 个 Worker 同时写；其余并行能力只用于审阅/调研类只读任务。
- `tests/` 入库后，worktree 内可直接跑 TestRunner；入库前不得给写卡派"加回归断言"的验收条件。
- **判"会不会入库"必须以 `git add -n` 为准**：`git check-ignore` 对带嵌套 `.git` 的目录或带尾斜杠的路径可能误报命中（2026-11-14 实测：报 `.gitignore:49` 命中，而该行为空、`git add` 实际会加入）。
- 未跟踪项计数用 `git status --porcelain -uall`，不加 `-uall` 会把目录折叠成一行，条数少一半以上。

**集成与收口（写卡合并）**

- **只有 Lead 合并**，串行执行：一张卡自测通过 → 合入 → 跑 §5.6 全套 → 绿了才合下一张。写域不相交不改变"串行合并"这条。
- **合并顺序**按依赖卡拓扑序；无依赖按评审 ROI 排。合并前确认该卡 HEAD 是自测过的提交。
- **冲突裁决**：同一文件冲突由 Lead 裁决，公共文件（§5.1）冲突一律保留 Lead 版本；裁决写进 ledger（`Ruling: ...`）。
- **失败与降级**：自测失败不合并，退回 Worker；两轮仍失败则拆卡或由 Lead 接管，并在 ledger 记裁决与代价。
- **合并后变红**：整卡回退（`git revert`/`git reset` 到合并前），不带病继续；修复另起写卡。
- 每张卡合并后在 ledger 记一行：`Task <N>: merged <base7>..<head7>`。

### 5.5 审阅协议

**定级**（沿用 `review-2.44.2.md` 口径）

| 级别 | 含义 | 处置 |
| --- | --- | --- |
| P0 | 启动必崩 / 必丢数据 / 安全 | 立即停线，报告内单列 |
| P1 | 用户可感功能错误、数据风险、验证链说谎 | 本次修（修复另起写卡） |
| P2 | 健壮性、可维护性、明显退化 | 记录，排期 |
| P3 | 风格、注释、文档瑕疵 | 记录，不排期 |

**证据要求**：每条 finding 必须有 `文件:行`、触发条件、可观察后果。没有行号的"感觉不对"不进报告。

**交叉复核**：P0/P1 由提出者以外的 agent 独立核对一次，结论三选一——确认、降级（附理由）、驳回（附理由）。复核是**独立一轮**（预算 20 分钟），不占 Worker 的 40 分钟取证轮；超时不延期，未复核条目单列「待复核」，**不得**进入正文定级。驳回条目留在附录并注明理由，不删除。

**误报率口径**：Lead 从 P1 中随机抽 20%（不足 5 条则全量）独立复核，被驳回或降级的比例即误报率；抽样与结论写进报告附录。预算 15 分钟，计入汇总时间。**P1 为 0 时**退化为从 P2 中随机抽 20%（不足 5 条则全量），并在附录写明抽样池构成（含被降级的原 P1），否则误报率不可复现。

**去重**：Lead 合并时按"同一根因"合并，保留多来源引用（如 `S-01 / C-1` 同根）。

**争议**：复核者与提出者结论不一致时，Lead 裁决；Lead 不得直接采纳任何一方而未读代码。

### 5.6 验证门禁串行协议

顺序固定：`dotnet build -c Release` → `tasklist | findstr MirrorpondHUD`（确认无实例）→ `bin\Release\MirrorpondHUD.exe --selftest --isolated` → `dotnet run --project tests\TestRunner\TestRunner.csproj -c Release` → 按需截图 → `dotnet format --verify-no-changes` → `tools/check-empty-catches.ps1`。

- **写卡合入前**：作者自测 `build` + 与本卡相关的断言/截图（允许在 worktree 内跑）。
- **合并后**：Verifier 在主线工作区跑全套一次，结果进报告。
- 每步贴命令 + 退出码 + 关键输出行；失败即停，不跳过后续步骤继续"看看再说"。
- 只读审阅任务不要求跑全套；但若审阅中发现构建/自检相关断言，Verifier 需跑一次以确认结论。

### 5.7 四类工作的形态

| 类型 | 并行方式 | 写域 | 审阅者 | 门禁 |
| --- | --- | --- | --- | --- |
| 审阅 | 按维度扇出，只读 | 无 | 交叉复核 P0/P1 | 不需要（必要时补跑） |
| 实现 / 重构 | 按程序集/卡插件切片 | 互斥前缀；公共文件归 Lead | 非作者看 diff | 写卡自测 + 合并后全套 |
| 修 bug | 按缺陷簇切片，先复现再改 | 同上 | 修复者与复核者分离 | 写卡自测 + 合并后全套 + 回归断言进 `tests/` |
| 文档 / 调研 | 按文档域切片 | `docs/` 下互斥 | 对照代码核对事实 | 不需要 |

### 5.8 产出与落点

- 审阅产出：`docs/review/YYYY-MM-DD-<主题>.md`，含一页结论、数字表、分维度条目、附录（复核记录、驳回项、误报率抽样、历史项复核）。
- 方法沉淀：本文件；AGENTS.md 末尾加一节引用（我的裁决，见 §7.1）。
- 样板作业报告：`docs/review/2026-11-14-parallel-review.md`。

### 5.9 失败模式与禁止事项

- 禁止 agent 自行改版本号、`AGENTS.md`、`.editorconfig`、`.gitignore`、`tools/` 基线；
- 禁止并行跑 `--selftest` / `--screenshot`；禁止伪造绿灯；
- 禁止"顺手整理"无关代码、批量合并空 catch、重排 P/Invoke；
- 禁止把未经复核的 P0/P1 直接写进报告正文；
- 禁止在一次提交里混多个主题；纯格式化单独提交并进 `.git-blame-ignore-revs`。

### 6.4 覆盖口径、时间盒与验收

- **覆盖口径**：报告一页结论只允许写"必查清单 7 项全覆盖 + 抽样 N 个文件/维度"，不得宣称"全仓无 P0"。
- 每 Worker 取证轮 ≤ 40 分钟；交叉复核独立一轮 ≤ 20 分钟；Lead 汇总（含误报率抽样）≤ 20 分钟。
- 超时规则：到点即交已核实部分，未核实内容单列"待复核"，不得为了凑完整而延期或降低证据标准。
- 验收：P0/P1 100% 交叉复核；每条 finding 有 `文件:行`；误报率按 §5.5 口径计算并写入附录；产出一份 `docs/review/2026-11-14-parallel-review.md`；未提交改动的处置建议明确到"入库 / 排除 / 归位"。

## 7. 已裁决与仍待确认

### 7.1 我的裁决（builder check 问题 5 条 + 2 条收尾）

1. **执行载体**（Q3）：Worker 用 Lead spawn 的 durable teammate 真并行，不用 workflow 脚本、不串行。
